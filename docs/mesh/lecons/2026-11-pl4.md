## 1 · Phases construites en parallèle, jamais vérifiées assemblées

**Défaut.** Le test de forme des fiches (`scripts/mesh/__tests__/agents.test.mjs`, phase 2)
exige exactement dix sections `##` ; les fiches A1 et A2 (phase 5) ajoutaient `## Méthode`.
Chaque phase était verte sur sa propre base ; une fois les deux sur develop, le job
`click-budget` (qui lance aussi les tests du mesh) est passé au rouge. #365 en a hérité sur
quatre poussées (`d52050b`, `2d8ce09`, `cc9ade4`, `20aae86` : `not ok … A1-retrospecteur.md
respects the template`). Corrigé par #366.

**Cause racine.** Pourquoi rouge sur develop ? Deux PR vertes chacune contre une base
différente. Pourquoi personne ne l'a vu avant le merge ? Aucune étape ne relance les contrôles
sur la branche **à jour** de develop, et GitHub n'exige pas une branche à jour (develop non
protégé, leçon 8). Pourquoi les auteurs des fiches A1/A2 ne l'ont pas vu ? Les contrôles du
mesh ne figuraient pas dans les consignes de construction. → Cause dans le mesh : la fiche L1
« rebase » sans « re-vérifie », et le skill ne liste pas les contrôles locaux.

**Garde-fou.** L1 fait un *contrôle d'assemblage* (tests du mesh fichier par fichier,
`route-budget`, `check-numerotation`) sur la branche à jour avant de demander le merge ; les
constructeurs relancent ces contrôles après chaque `git merge origin/develop`.

**Hypothèse mesurable.** Sur les cas de L1, le taux de réussite monte (cas
`l1-assemblage-develop-a-jour`), sans régression ailleurs.

## 2 · Garde-fous du mesh jamais exécutés réellement

**Défaut.** Le job `mutation / web` (`mesh-mutation.yml`, phase 3) n'avait jamais tourné : il
ne se déclenche que sur `web/lib/**` ou `packages/api-client/**`, et #365 a été la première
PR à les toucher. Trois défauts en cascade (#369 corrige la syntaxe `pnpm dlx` ; #372 reste
ouvert : `typescript` absent du bac à sable, Vitest 5 installé par `dlx` contre Vitest 2 du
dépôt, `api-client` invisible). Le job est encore rouge sur le dernier commit de #365
(`0e20967`, run 44054821170). Par ailleurs, au commit `1475806` `click-budget` a échoué :
`/changer-mot-de-passe`, atteinte seulement par redirection, sortait en route orpheline, et
`/mot-de-passe-oublie` restait dans `liensMorts` ; corrigé à la main au commit suivant
(`6c1e691`).

**Cause racine.** Pourquoi trois défauts d'un coup ? Le job n'a jamais été exécuté. Pourquoi ?
La phase 3 l'a considéré livré sur une validation YAML ; rien ne demande une exécution réelle
d'un garde-fou conditionnel. Pour le budget de clics : la doc ne disait pas qu'une page atteinte
seulement par redirection conditionnelle doit être déclarée, et le constructeur n'a pas lancé
`route-budget` avant de pousser (leçon 6). → Cause dans le mesh : définition de « livré »
absente pour les garde-fous ; aucun vérificateur ne la réclame.

**Garde-fou.** Règle : un job/script/réglage du mesh n'est livré qu'après une exécution réelle
sur un cas qui le déclenche. V1 en fait un constat *important*. `ROUTES-BUDGET.md` documente
la limite « pages atteintes par redirection ». **Non touché** : le workflow lui-même
(`.github/**`, décision humaine tracée en #372).

**Hypothèse mesurable.** Sur les cas de V1, le taux de réussite monte
(`v1-job-mesh-jamais-execute`).

## 3 · Promesse de l'écran non confrontée au backend

**Défaut.** La spec de porte 2 (#364) faisait dire à l'écran « il te ré-émet un identifiant et
un mot de passe tout neufs » et « à usage unique et expire après 7 jours », avec un lien
« Rejoindre ma classe » vers `/rejoindre`. Le code disait autre chose : code de classe
multi-usage (40) valable 14 jours (`ClasseController.java:43-44`, `V14`), et `/rejoindre`
**crée un nouveau compte** (progression perdue). Veto V5 au tour 1 ; la PR a été reprise côté
backend (le prof réinitialise le compte existant, ADR 0036).

**Cause racine.** Pourquoi ces phrases ? U5 a écrit les textes à partir des critères de la fiche
besoin (AC6 : « ≤ 7 j, usage unique ») et du nom du flux (`/rejoindre`), pas de ce que le code
fait. Pourquoi B3 les a-t-il implémentées ? La spec UI était complète au sens du contrat (états,
composants). Pourquoi trouvé en porte 5 seulement ? La grille de V5 visait les **valeurs**
inventées (constantes, `Math.random`), pas les **phrases** qui promettent un comportement.
→ Cause dans le mesh : ni le contrat de spec UI ni la grille V5 n'exigent une source par
promesse.

**Garde-fou.** U5 : chaque phrase factuelle porte dans la spec le `fichier:ligne` qui la rend
vraie, et un flux existant est décrit par ce qu'il fait. V5 : « Promesses de l'écran »
confrontées au **code**, pas à la spec ; promesse fausse faite à un mineur = *blocking*.

**Hypothèse mesurable.** Sur les cas de V5, le taux de réussite monte
(`v5-promesse-ecran-non-tenue`), sans régression sur U5.

## 4 · Concurrence en authentification trouvée tard

**Défaut.** Deux courses découvertes en vérification : **I1** (tour 3) — une connexion avec
l'ancien mot de passe ou un ancien provisoire, intercalée avec une réinitialisation, consommait
le provisoire tout juste émis ; **N1** (porte 5 finale) — une connexion qui lisait le compte
**sans verrou** réécrivait l'ancien état par-dessus une réinitialisation. Corrigés par un
`UPDATE` conditionnel puis `LoginAuditHandler` sous verrou (`d814e3a`), tests à contre-épreuve.

**Cause racine.** Pourquoi deux tours ? Le plan technique décrivait la réinitialisation, pas son
interaction avec la connexion existante. Pourquoi ? Ni la fiche B1 ni la règle backend ne
demandent d'énumérer les paires concurrentes d'un changement d'état d'authentification, et le
saboteur (S3) attaque l'interface, pas les transactions. → Cause dans le mesh : contrat de plan
technique muet sur la concurrence.

**Garde-fou.** Règle backend « Concurrency on authentication and account state » (paires
nommées, lecture sous verrou ou `UPDATE` conditionnel, test d'entrelacement à contre-épreuve) ;
B1 l'exige dans le plan.

**Hypothèse mesurable.** Sur les cas de B1, le taux de réussite monte
(`b1-concurrence-connexion-reinitialisation`).

## 5 · Numéros en collision entre branches parallèles

**Défaut.** #365 et #357 ont chacune créé `docs/adr/0036-…` ; une fois #365 mergée, #357
doit renuméroter (0039, 0037 et 0038 étant annoncés par #371 et #370 dans des commentaires).
Côté Flyway, #365 ajoute `V43` et #357 `V44` : merger #357 d'abord aurait fait refuser `V43`
en staging ; #365 a modifié `V43` en place pour ne pas décaler l'ordre.

**Cause racine.** Pourquoi la collision ? Chaque branche a pris « le numéro suivant » vu
depuis elle-même (`P3` : « numéro suivant »). Pourquoi pas vu ? Aucun contrôle ne compare les
numéros à la base ni aux PR ouvertes ; la réservation était informelle, après coup.
→ Cause dans le mesh : contrat ADR sans réservation, aucun check.

**Garde-fou.** `scripts/mesh/check-numerotation.mjs` (doublons sur la branche ; avec `--base`,
numéro déjà pris sur develop ou migration en dessous de sa plus haute version ; avec
`--open-prs`, numéro pris par une autre PR ouverte). `numerotation.test.mjs` tourne dans le job
`click-budget` (il lance tous les `scripts/mesh/__tests__/*.test.mjs`) : il garde develop sans
doublon et fige les règles de collision (dont le cas 0036 et l'ordre V43/V44). P3 et B1
**réservent** le numéro dans l'issue. Contre-épreuve faite : un ADR `0036-…` et une
`V40__…` ajoutés à blanc font échouer le check.

**Hypothèse mesurable.** Sur les cas de P3, le taux de réussite monte
(`p3-numero-adr-deja-reserve`).

## 6 · Hygiène PR et commits

**Défauts.**
- Le corps de #365 se terminait par « Ferme #364. » : GitHub ne reconnaît que les mots-clés
  anglais, `closingIssuesReferences` était vide et #364 a été fermée à la main après le merge.
  Le gabarit de PR (`.github/pull_request_template.md`) porte pourtant `Closes #`.
- **Bug du hook `commit-msg`** (reproduit) : `git merge --no-edit` écrit
  « Merge branch … » **sans retour à la ligne final** ; la boucle `while read` ignorait cette
  dernière ligne, le sujet lu était vide, et l'exemption des merges ne jouait jamais. D'où trois
  commits de merge réécrits à la main (`a42f92d`, `2f03f60`, `77d96c2`).
- Prettier lancé sur un glob a reformaté sept fichiers hors sujet, annulés par `cc9ade4`.
- Les constructeurs ne lançaient pas les contrôles du mesh avant de pousser (`1475806`, leçon 2).

**Cause racine.** Le mesh n'avait aucune vérification de la référence de fermeture (L1 résume,
ne contrôle pas) ; le hook avait un défaut jamais testé (aucun test du hook) ; le skill `/feature`
ne disait ni quoi lancer avant un push ni comment formater.

**Garde-fou.** Hook corrigé (`|| [ -n "$line" ]`) et `commit-msg-hook.test.mjs` (contre-épreuve :
l'ancien hook échoue 2 tests sur 3). L1 vérifie `closingIssuesReferences` avant le merge. Règle
`mesh-hygiene.md` (contrôles avant push, `Closes #` en anglais, Prettier sur les fichiers
modifiés). V1 compte un reformatage hors sujet comme *important*.

**Hypothèse mesurable.** Sur les cas de L1, le taux de réussite monte
(`l1-mot-cle-fermeture-anglais`).

## 7 · Test e2e instable

**Défaut.** `web/e2e/mode-interactif.spec.ts:86` (*switching modes keeps the position and the
answer being typed*) a échoué deux fois (essai + retry Playwright, `toHaveURL` après `Escape`,
`ECONNRESET` côté `next dev`) au run 43895845664 tentative 1, puis est passé à la relance. La
session de construction de #365 rapporte aussi des relances locales (non tracées).

**Cause racine.** Pourquoi pas de ticket ? Une relance au vert ne produit aucun signal ; la fiche
V3 décrit les « tests instables » dans son rapport, mais rien ne la déclenche hors de sa revue,
et `retries: 1` en CI absorbe un échec isolé. → Cause dans le mesh : déclencheur absent.

**Garde-fou.** V3 : un job relancé jusqu'au vert ouvre ou complète un ticket `mesh:inbox`.
Appliqué ici : **#374**. Le test lui-même n'est pas touché (hors périmètre, code web).

**Hypothèse mesurable.** Sur les cas de V3, le taux de réussite monte (`v3-relance-sans-ticket`).

## 8 · `develop` sans protection de branche

**Constat.** `gh api repos/BrioOrg/brio/branches/develop` → `protected: false`, aucun ruleset.
Le garde-fou non négociable « aucun push sur develop » ne tient que par `.githooks/pre-push`,
local et contournable (`--no-verify`, clone sans `scripts/setup.sh`). Une protection exigeant
aussi une branche à jour et des checks verts aurait arrêté l'incident 1.

**Garde-fou.** Aucun versionné : **décision N3 pour l'humain**, rien n'a été modifié. Consigné
dans la règle `mesh-hygiene.md` pour que les agents ne s'appuient pas sur une protection qui
n'existe pas.

## 9 · Journal du mesh vide

**Défaut.** `mesh/journal/` ne contenait que `.gitkeep` : aucune des actions de PL-4 (portes,
verdicts, veto V5, arbitrages N3, désaccords) n'a été journalisée. A1 n'a donc ni désaccords
humains à compter ni base pour l'autonomie (« mesurer, pas deviner »).

**Cause racine.** `JOURNAL.md` dit « chaque agent écrit sa propre ligne », mais en mode 1 les
agents sont joués par une session ; le skill `/feature` ne disait pas qui écrit, quand, ni où.

**Garde-fou.** Le skill `/feature` : la session écrit la ligne de chaque porte, verdict, veto et
arbitrage dans le commit de la porte. `journal.test.mjs` vérifie le format de chaque ligne
(champs, `ts` UTC dans le mois du fichier, `level` N0–N3, `note_humaine` si désaccord).
`mesh/journal/2026-11.jsonl` porte les premières lignes (celles de cette rétro). Les jetons y
sont `null` : non mesurés en mode 1.

## Ce que A2 n'a pas pu faire

- **Aucune mesure.** Le runner d'évals (`scripts/mesh/run-evals.sh`, prévu par `TUNING.md`)
  n'existe pas, et le jeu caché est vide (`mesh/evals/empreintes.json` : `cases: []`,
  `HIDDEN.md` : option de stockage non tranchée). Aucune leçon n'a de score public ni caché,
  base ou candidat ; aucun verdict `gain` / `neutre` / `régression` n'a été rendu.
- Le verdict attendu, selon `TUNING.md`, serait **`non mesurable`** (moins de 5 cas cachés par
  agent) : merge humain explicite possible, **aucune montée d'autonomie**.
- **Écart au processus, assumé** : `TUNING.md` veut qu'A3 ne versionne qu'après un `gain`. Ici
  A3 a versionné sur demande humaine explicite (session de pilotage), sans verdict. Les cas
  publics ajoutés sont les futurs supports de mesure ; ils ne prouvent rien tant qu'A2 ne les
  a pas passés.
- Écart aussi à « trois leçons au plus, un agent cible par PR » : neuf leçons dans une PR,
  demandées ainsi pour la première rétro. À scinder si l'humain le préfère.
