# 0018 — Base légale du traitement des données élèves

- **Status**: Accepted
- **Date**: 2026-09-14
- **Deciders**: Pierce Broudin

## Context

ADR 0016 §5 required parental consent for every élève account and stored
`email_titulaire_legal` on every `compte` of role `eleve`. That design was
calibrated for a direct-to-family product — a student downloads the app and
their parent validates via email.

Issue #61 introduces a different scenario: a school deploys Brio as part of
its institutional mission and students join via a class code distributed by the
teacher on a whiteboard. This is how ENT, Pronote, and school-provided edtech
operate in France. The legal basis is no longer individual consent (GDPR
art. 6(1)(a)); it is the pursuit of a task carried out in the public interest
(art. 6(1)(e)), with Brio acting as a data processor (sous-traitant, art. 28).

Under the mission basis, parental consent is not required — because consent
is not the processing basis being used. Parents are informed through the school
(not asked), and the school is the controller that authorises the processing.

The two bases are not interchangeable. Declaring one while implementing the
other is a GDPR violation. This ADR records both paths, the conditions under
which each applies, and the schema column that makes the basis queryable.

## Decision

### 1. Two paths, selected by the class's établissement

| | Path A (mission d'intérêt public) | Path B (consentement) |
|---|---|---|
| **Legal basis** | art. 6(1)(e) — public-interest mission | art. 6(1)(a) — individual consent |
| **Controller** | The établissement | Brio |
| **Processing chain** | Brio acts as sous-traitant (art. 28) | Brio is responsable de traitement |
| **Parent action** | Informed by school (not asked) | Validates email before account is active |
| **Account status at creation** | `actif` immediately | `en_attente_consentement` |
| **`email_titulaire_legal`** | Not collected | Required |
| **identifiantConnexion** | Generated by server, shown once | Generated by server, shown once |

Path B is ADR 0016 §5 unchanged. Path A is the addition introduced by this ADR.

Which path applies is determined by the class's établissement: a class may use
path A only if its `etablissement.convention_signee_le` and
`etablissement.convention_reference` are both non-null. A class whose
établissement has unsigned or absent convention fields falls back to path B.

### 2. `base_legale` column on `identite.comptes`

A new column `base_legale VARCHAR(30)` records which path was used at account
creation. Valid values: `'consentement'` and `'mission_etablissement'`.
The column is non-null for `role = 'eleve'` (enforced by a CHECK constraint);
null is acceptable for adult roles where no legal basis choice was made.

The original `eleve_minimise` constraint is updated:

```sql
-- Before (ADR 0016):
CHECK (role != 'eleve' OR email_titulaire_legal IS NOT NULL)

-- After (ADR 0018):
CHECK (role != 'eleve'
       OR base_legale = 'mission_etablissement'
       OR email_titulaire_legal IS NOT NULL)
```

This keeps the invariant intact for path B accounts (they still cannot exist
without a parent email) while allowing path A accounts to omit it.

### 3. Convention gate — build the code, block the activation

The code for path A is implemented unconditionally. What is gated is the
ability to actually use path A for a real student: it requires
`etablissement.convention_signee_le IS NOT NULL AND
etablissement.convention_reference IS NOT NULL`.

This gate exists because deploying path A without a signed convention would
mean processing a minor's data on a legal basis that does not yet exist.
The `POST /api/classes/rejoindre` endpoint checks these fields before creating
any account and returns 403 if they are absent.

**Before any real établissement can enable path A**, the following must be in
place (outside the scope of this ADR, blocked until legal consultation):
- A convention template reviewed by a DPO
- A registre des traitements entry covering `mission_etablissement` accounts
- A parent information notice delivered by the school

### 4. Deviation from ADR 0016 §2: `nom_affiche` supplied by the student

ADR 0016 §2 states that `nom_affiche` in `identite.inscriptions` is typed by
the teacher when they build their class list. Path A removes the teacher from
the enrollment flow entirely. The student must therefore supply their own
`nom_affiche` at join time.

The class-scope invariant is preserved: the name lives on `inscriptions`,
not on `comptes`. Brio does not validate or verify it; a surname typed there
is the student's own act. Teachers can edit `nom_affiche` after the fact from
the class list.

Label guidance for the UI: « Ton prénom, comme ton prof te connaît » — cap
around 30 characters.

### 5. `identifiantConnexion` generated by the server

For path A, `identifiantConnexion` is generated by the server at join time
using a 10-character unambiguous alphanumeric string (alphabet excludes 0, 1,
O, I). It is returned exactly once in the join response (`EleveInscritInfo`)
so the student can note it down; it is never returned in any other response
type. ADR 0016 §4's invariant (identifiantConnexion never appears in a
response type intended for display) remains in force for all other endpoints.

### 6. Class codes

- Format: 12 characters, alphabet `23456789ABCDEFGHJKMNPQRSTUVWXYZ`
  (excludes `0`, `1`, `I`, `O` — legible off a whiteboard)
- Storage: SHA-256 hash of the raw code; raw code returned once at generation
- Default TTL: 14 days; caller-provided override up to 60 days
- Default `usages_max`: 40; caller-provided override up to 200
- One active code per class; generating a new code invalidates the previous one
- Teachers can view code metadata (usage count, expiry) and revoke the code;
  only ADMIN\_BRIO can generate new codes

## Consequences

### Positive

- Two processing bases are explicit in the schema — no ambiguity about which
  legal framework applies to a given account.
- The convention gate prevents path A from being accidentally used without a
  legal foundation.
- Path A eliminates the parent-email bottleneck for school deployments, which
  is the practical blocker for B2B2C adoption.

### Negative / trade-offs

- Adding `base_legale` to `comptes` means every élève account creation point
  must supply the value; omitting it for a path B account in application code
  violates the DB constraint.
- Storing `nom_affiche` student-supplied rather than teacher-supplied weakens
  the teacher's authorship of their class roster. The edit affordance partially
  restores it.
- Legal consultation on the convention template, the registre des traitements,
  and the parent information notice is a hard prerequisite before real-school
  deployment of path A. This work is not tracked in this ADR.

### Follow-ups

- Convention template + legal consultation
- Registre des traitements entry for `mission_etablissement` accounts
- Parent information notice delivered by the établissement
- Rate limiting on `POST /api/classes/rejoindre` (same as login endpoint)
- `ROLE_ADMIN_ETAB` class management (scoped to own établissement) — deferred
  until second établissement onboarded
- Teacher-class assignment flow (`enseignant_principal_id` currently nullable)

## Alternatives considered

- **Collective teacher attestation for parental consent** — rejected in ADR
  0016 §5 for the consent path; not applicable here (path A uses a different
  basis, not teacher attestation of consent).

- **No `base_legale` column; infer basis from presence of `email_titulaire_legal`**
  — rejected. Inference is not an audit trail. When a regulator asks which
  basis was used for a given account, the answer must be a stored fact, not
  a derivation.

- **Single path only (always consent)** — rejected. Schools will not deploy
  a tool that routes parental consent outside the school's own information
  system. This is the practical reality of French public-sector edtech.

- **Separate account tables per path** — rejected. The account structure
  (ADR 0016) is orthogonal to the legal basis. Adding a column and a constraint
  is the minimal change that preserves the invariants.
